# Автоматизация предварительной приёмки Run 4

Владелец согласовал план 17.11.2026 в чате. Первый этап был аудитом только на чтение.
Цель — автоматизировать предварительные проверки перед приёмкой на ГУ.
Исторические [план](../acceptance/test-plan-run4.md) и [APK Run 4](../acceptance/build-run4.md) учитываются отдельно от актуальной сборки.
Результаты Emulator и WSL не подтверждают приёмку ГУ, USB или FM.

## Полномочия и ограничения

Программные изменения, worktree, тесты, коммиты, push, PR и Issues через `gh` разрешены.
Владелец подтвердил эти полномочия в текущей сессии; повторное согласование программной работы не требуется.
Merge выполняет владелец. Каждый связный блок проходит [процесс Codex](../agents/codex-implementation.md).
Следующий блок начинается после merge предыдущего. Программный объём повторного согласования не требует.

1. Активные USB-сеансы требуют отдельного разрешения владельца.
2. Изменение драйверов и USB/IP требует отдельного разрешения.
3. Аварийное завершение Emulator требует отдельного разрешения.
4. Установка и обновление программ требуют отдельного согласования.
5. EEPROM, firmware и bias tee operations запрещены.
6. Аппаратные проверки идут последовательно: Super Radio, затем RTL-SDR V4.
7. Android-драйвер RTL-SDR и FM DSP остаются открытыми задачами [#159](https://github.com/krasotinpa/heterodyne-fm/issues/159)/[#160](https://github.com/krasotinpa/heterodyne-fm/issues/160).

### Блок 1: паспорт и изоляция

Единая точка входа — `build-support/preflight.py`. Новые зависимости не нужны.
Для офлайн gate runner переиспользует `build-support/validate.sh`.
Проверки выполняются до установки APK, запуска AVD или ADB-команд с воздействием.

1. Паспорт хранит commit, dirty-состояние, SHA-256 APK, сертификат, package, ABI и версии среды.
2. Runner сверяет фактический APK с явно выбранным паспортом и назначением сборки.
3. Исторический APK допускается только как исторический артефакт; он не заменяет актуальный preflight APK.
4. Стенд использует собственную копию AVD, отдельный ADB server и явный serial.
5. Runner проверяет принадлежность процессов и дисков; существующие AVD остаются неизменными.
6. Неоднозначные или недоступные сведения приводят к отказу, а не к продолжению.
7. Тесты проверяют публичный CLI: подмена APK, stale/dirty сборка, несоответствие паспорта и чужой стенд.
8. Instrumented runner проверяется до создания Application; недоступный UsbManager запрещает запуск.

Создание и запуск стенда автоматизируются после появления проверок принадлежности.
В первом блоке допустимы проверки подготовленного стенда без запуска Android-сценариев.

### Остальные программные требования

1. Настоящий HTTPS проверяется отдельно от fixtures; отчёт различает источники результата.
2. Visual использует 1280×720, 1024×600 и 1920×1080, масштаб шрифта 1,0 и 1,3.
3. Светлая и тёмная темы, основные экраны и ошибки входят в матрицу Visual.
4. Агент просматривает фактические PNG. Эталоны автоматически не обновляются.
5. Reboot и cold boot сохраняют диски; `-wipe-data` запрещён.
6. Синтетический звук проверяет Android AudioTrack, но не радиоприём и маршрут ГУ.
7. Исправления найденных продуктовых дефектов выполняются отдельными задачами после triage.

## Режимы runner

| Режим | Назначение |
|---|---|
| `offline` | Существующий офлайн validation gate |
| `android-ui` | Сквозные UI-сценарии собственного AVD |
| `visual` | PNG и визуальная матрица |
| `simulated-receiver` | Fake Receiver, transport и PCM |
| `emulator-reboot` | Обычный reboot собственного стенда |
| `emulator-power-loss` | Проверка потери питания; требует отдельного разрешения на аварийное завершение |
| `super-radio-hardware` | Super Radio; требует отдельного разрешения на активный USB-сеанс |
| `rtl-sdr-hardware` | RTL-SDR V4 после Super Radio; требует разрешения и готового драйвера/DSP |
| `preflight-all-safe` | Только реализованные безопасные режимы; неполный набор не выдаёт общий passed |

Нереализованные и недопущенные режимы отказывают до воздействия.
Наличие имени режима не означает его готовность.

## CLI первого блока

Команды выполняй из собственного worktree. `passport` выводит JSON в stdout.
Сохраняй паспорта и журналы локально в `.scratch/`; APK не добавляй в Git.
Используй явно выбранный доверенный паспорт. Создание паспорта само по себе не доказывает происхождение бинарного кода.
`source_basis` обозначает сверку версии с переданным commit; воспроизводимая сборка здесь не проверяется.
`inspection_environment` содержит версии среды проверки, а не недоказанные версии исторической среды сборки.

```bash
python3.12 build-support/preflight.py passport --apk /absolute/app.apk --source-commit FULL_SHA --purpose current > .scratch/passport.json
python3.12 build-support/preflight.py check --apk /absolute/app.apk --passport .scratch/passport.json
python3.12 build-support/preflight.py run offline --apk /absolute/app.apk --passport .scratch/passport.json
python3.12 build-support/preflight.py fixture --manifest .scratch/preflight-fixtures/NAME/fixture.json
```

Для исторического APK используй `--purpose historical`. Его можно проверить через `check`; `run` его отвергает.
Для отдельного синтетического APK используй `--purpose preflight`; он требует package `fm.heterodyne.app.preflight`.
Актуальная сборка требует чистый APK текущего HEAD, чистое tracked-дерево и ABI x86_64.
Проверка `run offline` предшествует вызову существующего `validate.sh`; его ненулевой exit code возвращается вызывающему процессу.

Manifest стенда содержит `schema: 1`, `state`, `avd_name`, `adb_port`, `emulator_port`, `serial`.
Файлы AVD находятся в `avd/NAME.avd` рядом с manifest; указатель — `avd/NAME.ini`.
Для `state: running` добавь `emulator_process` и `adb_process`: PID и строковый `start_ticks` из `/proc/PID/stat`.
Runner проверяет бинарные файлы, время запуска PID, аргументы и владение слушающими портами через `/proc`.
Он проверяет пути дисков и цепочки QCOW2 через установленный `qemu-img info -U --backing-chain`.
При недоступных `/proc` или инструментах команда отказывает; она не меняет права среды.
`state: stopped` проверяет только структуру копии; он не доказывает отсутствие скрытых процессов.
Успех `fixture` всегда содержит `launch_admitted: false`: команды запуска и остановки стенда ещё не реализованы.
Android-режимы и `preflight-all-safe` пока отказывают до воздействия.

## Отчёты и Issues

После прогонов runner сохраняет четыре раздела:

1. **Run 4 Preflight Report**: паспорт, стенд, шаги, ожидание, факт, статусы, evidence, exit codes.
2. **Defect and Issue Report**: воспроизводимые actionable findings, поиск дубликатов, ссылки Issues.
3. **Remaining Car Tests**: все оставшиеся проверки ГУ и причины blocked/not tested.
4. **Skills Execution Report**: применённые скиллы, фактические действия, ограничения.

Codex диагностирует actionable findings и ищет существующие Issues через `gh`.
Он создаёт новый Issue или дополняет существующий после исключения дубликата.
Ошибка инфраструктуры и продуктовый дефект записываются с отдельными причинами.

## Проверка каждого блока

Применяй `ponytail full`, проектный `heterodyne-graphify` и `tdd`.
Границы тестирования заданы этим планом и [test-plan](../test-plan.md); повторное согласование границ не требуется.
Для дефектов применяй `diagnosing-bugs`. После полного gate выполняй одну независимую волну Standards и Spec.
Reviewer только читает. Исполнитель объединяет fixes и повторяет gate один раз.
Для PR применяй скилл `pr`; merge оставляй владельцу.

План завершён после реализации блоков, проверок и успешного CI последнего PR.
Готовность предварительных проверок не закрывает аппаратную приёмку [#89](https://github.com/krasotinpa/heterodyne-fm/issues/89).

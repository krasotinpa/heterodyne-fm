# G4-7: playSelect в FM и роль байта b7

Исполнитель — Claude Code в Windows (через Windows PowerShell). Уровень воздействия E. Билет: [#49](https://github.com/krasotinpa/super-radio-android/issues/49).
Цель — проверить playSelect в FM и установить роль байта `<b7>`. Предыдущий опыт — [g4-6-report.md](../research/g4-6-report.md).
Владелец 15.10.2026 одобрил два кадра playSelect. Параметры ниже вступают в силу после merge этого плана владельцем.
Кадры вне whitelist для AM (см. [command-catalog.md](../research/command-catalog.md)). Они разрешены только как кадры этого эксперимента, по одной сессии.

## Кадры

| Кадр | Что проверяет |
|---|---|
| P1: playSelect FM cid 29, `<b7>` = `20` | Работает ли playSelect в FM. Ожидание: «90.4 MHz» вместо «90.3 MHz» |
| P2: playSelect cid 28, `<b7>` = `00` | Роль `<b7>`. Если Модуль остался в FM «90.3 MHz» — байт игнорируется. Если перешёл в AM cid 28 «774 KHz» — байт задаёт диапазон |

Cid 29 — соседний с текущим (FM cid 28 «90.3 MHz» после G4-6): шаг 0,1 МГц, как TUNEUP/TUNEDOWN. Cid вне известного диапазона не используются.
Если после P2 Модуль окажется в AM, возврат — BAND в следующей сессии постоянной командой. Агент не добавляет кадров.

```text
60 с rAI ─▶ 90 с P1 ─▶ 120 с rAI ─▶ 150 с P2 ─▶ 180 с rAI ─▶ 300 с порт закрыт
```

| SEQ | Время от открытия | Команда | Кадр |
|---|---|---|---|
| 0 | 60 с | requestAllInfo | `FA 55 00 00 04 80 85 07 F4` |
| 1 | 90 с | playSelect P1 | `FA 55 01 00 07 80 82 20 1D 00 1D A4` |
| 2 | 120 с | requestAllInfo | `FA 55 02 00 04 80 85 07 F4` |
| 3 | 150 с | playSelect P2 | `FA 55 03 00 07 80 82 00 1C 00 1C C6` |
| 4 | 180 с | requestAllInfo | `FA 55 04 00 04 80 85 07 F4` |

Всего пять записей, каждая один раз, в указанном порядке.

## Условие запуска P1

P1 имеет смысл только в FM. Агент читает ответ на SEQ 0 из `g4-7-rx.bin` до 90 с. Если в `0x22` режим не FM (`тело[1]` >> 5 & 3 ≠ 1), агент создаёт `g4-7-stop.flag` до 90 с. Тогда P1 и P2 не отправляются, а требуется новое решение владельца.

## Границы

Схема, скрипты и проверки повторяют [g4-6-windows-plan.md](g4-6-windows-plan.md) и цепочку за ним. Имена `g4-6` заменяй на `g4-7`.
Отличия:

1. `$plan` содержит пять записей из таблицы, время `At` в миллисекундах.
2. Длительность цикла — 300 с; трасса — 780 с; пользователь наблюдает за Модулем 5 минут.
3. Порог перезапуска сессии до запуска скрипта — 300 с от старта трассы.
4. В порт пишутся ровно пять массивов из таблицы. Автоповтора нет.
5. Перед каждой отправкой скрипт проверяет `g4-7-stop.flag`. Пользователь создаёт флаг при любой аномалии.
6. Ожидание скрипта — до 12 вызовов по 30 с. Ожидание tshark — `-Timeout 480`.

## Что ожидать

1. После SEQ 0 — FM cid 28 «90.3 MHz», как в начале G4-6.
2. После P1 — `0x22` FM cid 29 «90.4 MHz» за менее чем 100 мс. Альтернативы: молчание, другой cid, `0x28`, смена диапазона.
3. После P2 — одно из двух: FM cid 28 «90.3 MHz» (байт игнорируется) или AM cid 28 «774 KHz» (байт задаёт диапазон).

## Критерии

| Вопрос | Ответ «да» | Ответ «нет» |
|---|---|---|
| playSelect работает в FM | P1 дал FM cid 29, нет побочных эффектов | P1 без изменений или с побочными эффектами |
| `<b7>` задаёт диапазон | P2 перевёл Модуль в AM | P2 оставил Модуль в FM |

Если P1 удался, агент предлагает владельцу строку whitelist для FM. Если нет — playSelect остаётся только для AM.

## Сводка и передача

Сводка и SHA — как в G4-6. Агент проверяет `bulk_out` вывода `analyze_session.py`: ровно пять пакетов, байты и порядок из таблицы, затем пишет `docs/research/g4-7-report.md`.
Строки whitelist вносит только владелец.

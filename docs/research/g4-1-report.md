# G4-1: одна отправка requestAllInfo

Дата: 14 октября 2026 года. Уровень воздействия E: одна команда из [command-catalog.md](command-catalog.md) по решению владельца.
Сбор выполнил Claude Code в Windows по [g4-windows-plan.md](../plans/g4-windows-plan.md); анализ выполнен в WSL.

## Итог

Через 0,5–2,4 мс после единственной отправки requestAllInfo пришли четыре Кадра: `0x27`, `0x22`, `0x24`, `0x21`.
Предыдущая посылка Модуля была за 1 043 мс до этого. Связь «команда → ответ» выведена по времени, а не доказана.
Это согласуется с моделью B и для TX; наблюдение одно, проверки чувствительности к SEQ не было.
Переподключения нет, cid станции тот же. В `0x22` изменился один байт неизвестного смысла: это может быть и эффектом команды.

```text
18:15:57.1149 хост → bulk OUT 0x03: FA 55 00 00 04 80 85 07 F4
      +0,5 мс Модуль → 0x27 версия, 0x22 текущая станция, 0x24 сигнал 3
      +2,4 мс Модуль → 0x21 список станций
      +957 мс обычный ритм: 0x26, 0x24 каждые 2 с
```

## Отправка

1. `g4.ps1` запущен один раз, exit code 0. Флаг `g4-sent.flag` создан. Строк `error` нет.
2. В трассе ровно один bulk OUT с данными: endpoint `0x03`, 18:15:57.114906 UTC (время отправки запроса URB), байты `fa 55 00 00 04 80 85 07 f4`.
3. `tx-begin` в `g4-reads.csv` — 18:15:57.1099, через 60,0 с после открытия порта; `tx-end` — через 6 мс, в буфере драйвера 0 байт.
4. Других данных хост Модулю не отправлял. Набор из 44 управляющих запросов за сессию совпадает с сеансом B G1b по составу и числу: перечисление при подключении, CDC при открытии, два `SET_CONTROL_LINE_STATE` 0 при закрытии в 18:17:57.

## Ответ

| Время от OUT | Пакет bulk IN | Кадры |
|---|---|---|
| +0,531 мс | 60 байт | SEQ 162 `0x27` `V3.04.20250530`, начало SEQ 163 `0x22` |
| +0,666 мс | 43 байта | конец SEQ 163 `0x22`, SEQ 164 `0x24 00 03` |
| +2,371 мс | 31 байт | SEQ 165 `0x21 c0` с записью «1044  KHz» |
| +957 мс | 34 байта | SEQ 166 `0x26`, SEQ 167 `0x24` — обычный ритм |

Предыдущий пакет от Модуля пришёл за 1 043 мс до OUT. Ответ не совпадает с периодической посылкой.
Набор ответа — подмножество стартовой пачки G1b: версия, текущая станция, сигнал, список станций. Кадров `0x28` и `0x23` в ответе нет.

`0x22` ответа отличается от стартового одним байтом и суммой: кадр +30 был `0x16`, стал `0x08`. cid `00 3a` тот же. Приложение производителя это поле не разбирает; смысл не установлен.

## Наблюдения пользователя

Дословно: «Звуков не было»; «нагрев слабый»; «на модуле индикаторов нет, индикаторый компьютера поведение не меняли».
Модуль был подключён к компьютеру без аудиотракта, поэтому отсутствие звуков ничего не говорит о радио. Нагрев сравнить не с чем: базовой оценки нет.
Переподключения не было: снимки PnP до и после отправки совпадают по SHA-256, а в трассе один адрес Модуля на всю сессию.

## Попутные наблюдения

1. Подключение → открытие порта: 63 с. Стартовая пачка снова оборвана на смещении 1229, как в сеансе A G1b; следующий Кадр — на 1240, SEQ 63 → 98.
   Обрыв на одном смещении в двух сеансах из трёх (в сеансе B его нет) — необъяснённая потеря. Пропуски SEQ разные: 7 и 35 Кадров.
2. Сигнал с антенной: `24 00 03` × 106, `24 00 04` × 10.

## Следующий шаг

1. Решение владельца: сделать requestAllInfo постоянной командой whitelist (повторяемый запрос) или оставить однократной.
2. Следующий кандидат G4 — команда со сменой состояния и проверяемым эффектом, например TUNEUP (`80 88`): ответ `0x22` с новым cid. Она меняет станцию, поэтому требует отдельного решения.

# G6a: звук Модуля через WSL и USB/IP

Дата: 15 октября 2026 года. Стенд: ноутбук, WSL `Ubuntu` 24.04.5, ядро `6.18.40.1-microsoft-standard-WSL2`, usbipd-win 5.3.0.
План: [g6a-wsl-audio-plan.md](../plans/g6a-wsl-audio-plan.md). Исполнители — владелец (Windows) и агент (WSL).

## Итог

1. Модуль отдаёт звук. На FM 90,3 МГц (Авторадио) владелец услышал речь, «звук чистый, без щелчков, треска или прерываний».
2. Драйвер Linux `snd-usb-audio` Модуль не принимает: поток разобран, но разбор блоков управления (`snd_usb_create_mixer`) завершается `-ENODEV`, и карта удаляется.
3. Звук берётся через libusb: захват IF 1, alt 1, изохронный приём с EP `0x81`. Приложение производителя по статическому анализу тоже читает поток через libusb.
4. В этой сессии до захвата радиокоманд не было: Модуль слал поток сразу после выбора alt 1. Холодный старт после отключения питания не проверялся. Без станции (AM 1044 кГц в помещении) это ровное шипение.
5. Поток: 48 кГц, 16 бит, 2 канала. Пакеты по 192 байта, раз в ~0,46 с — 198. Данные идут непрерывным потоком байтов: кадры пересекают границы пакетов. Начало кадра надо находить, а не считать от начала пакета.

Каждый вывод — одно наблюдение на одном стенде. Для ГУ это сильный признак, а не проверка: ядро ГУ старше, см. «Что это значит для ГУ».

```text
Модуль ─USB─ Windows (usbipd bind --force) ─USB/IP─ WSL
   IF 1 alt 1, EP 0x81 iso ── libusb (iso_capture) ── PCM 48 кГц ── WAV
   IF 3, EP 0x03/0x83 bulk ── libusb (cdc_send): rai, band, tuneup ── 0x22 FM 90.3
   snd-usb-audio: поток разобран → mixer -ENODEV → карта удалена
```

## Драйвер Linux

1. `cdc_acm` заблокирован до подключения (`install cdc_acm /bin/false`); `/dev/ttyACM*` не появлялся.
2. После `attach` драйвер `snd-usb-audio` занял IF 1, IF 0 остался без драйвера, звуковой карты нет. В `dmesg` об ошибке ничего.
3. С отладкой драйвера (`dynamic_debug`) видно: найден EP `0x81`, «Set sample rate 48000». Дальше — тишина.
4. kretprobe и function_graph показали: `snd_usb_parse_audio_interface` = 0, `snd_usb_add_audio_stream` = 0, `snd_usb_create_mixer` = −19 (`-ENODEV`).
   Затем `snd_card_register` и сразу `snd_card_free`.
5. Исходный код `sound/usb/card.c` v6.18 объясняет порядок: ошибка mixer → `__error` → `try_to_register_card` → `snd_card_free`; проба возвращает `-ENODEV`, ядро её не печатает.
6. `ignore_ctl_error=1` и `skip_validation=1` не помогли: ошибка — в разборе дескрипторов, а не в USB-запросе.

Гипотеза о причине: терминал с ID 1 имеет подтип `0x03` (Output Terminal) при длине и полях Input Terminal ([descriptor-map.md](descriptor-map.md)).
Тогда `bNrChannels` = 2 читается как `bSourceID`: «выходной» терминал 1 берёт источник из Feature Unit 2, а FU 2 — из терминала 1. Получается петля, и цепочка блоков не сходится. Исходник `mixer.c` в этой части не сверялся.
Windows на том же дескрипторе тоже не создала устройство записи.

Побочный эффект: после неудачной пробы IF 1 остаётся занят `snd-usb-audio`. Для захвата драйвер выгружался (`modprobe -r snd-usb-audio`).
`/proc/asound` в этом ядре нет (`CONFIG_SND_PROC_FS` выключен); шаги плана с `/proc/asound` невыполнимы.

## Захват через libusb

`iso_capture`: claim IF 1, `SET_INTERFACE` alt 1, 8 передач по 8 iso-пакетов по 312 байт, в конце alt 0. Запросов класса и vendor нет; Приложение производителя по статическому анализу, вероятно, ещё шлёт запрос частоты (`set_sample_rate_v1`).
Кроме двух записей был пробный захват 5 с ([iso-test5.txt](../../evidence/g6a-20261015T103554Z/iso-test5.txt)): 4496 пакетов, плохих 0.

| Запись | Станция | Пакеты | Плохие | Длины | Уровень (RMS / пик) | Ответ владельца |
|---|---|---|---|---|---|---|
| 29,3 с | AM 1044 кГц | 29 312 | 0 | 192 × 29 248, 198 × 64 | −20,6 / −5,7 dBFS, ровный ~3000 по секундам | «слышно только шипение, рчи или музыки нет»; «тресков, прерываний, или щелчков нет» |
| 28,7 с | FM 90,3 МГц | 28 680 | 0 | 192 × 28 616, 198 × 64 | −20,7 / −4,7 dBFS, от 748 до 4276 по секундам | «Слышна речь, музыки нет в фрагменте»; «Звук чистый, без щелчков, треска или прерываний» |

1. 192 байта = 48 стереокадров по 4 байта = 1 мс при 48 кГц. Пакет 198 байт — это 49,5 кадра, раз в ~0,46 с.
2. Выравнивание: после отбрасывания первых 2 байт записи AM каналы совпадают во всех кадрах, кроме одного — кадра 191, где кончаются начальные 4 мс нулей.
   Значит, данные — непрерывный поток байтов, пакеты по 198 байт сдвига не вносят, а кадры пересекают границы пакетов. Обычное для UAC1 «пакет = целые кадры» здесь не выполняется.
   Смещение было 2 байта во всех трёх захватах; почему, не установлено. Приложению надо находить начало кадра, например по совпадению каналов на моно-участке, а не задавать его жёстко.
3. EP асинхронный (`bmAttributes 5`): частота Модуля не привязана к часам хоста, на ГУ понадобится компенсация дрейфа.
4. FM: первые 20,6 с выровненной записи — точное моно (каналы равны), дальше каналы различаются в 33–68 % кадров каждой секунды. Среднее 85 % это скрывает.
   Модуль сам сообщает режим в `0x26`: «Mono» на 90,5 и 90,4 МГц, «Stereo» на 90,3 МГц с ~4 с после настройки. Во время записи CDC не читался; переход моно → стерео в записи — гипотеза о стерео-декодере или смешении по уровню сигнала.
5. Нулей 0,03 % (AM) и 0,3 % (FM), участков нулей длиннее 4 мс нет. «0 плохих пакетов» не доказывает, что USB/IP ничего не потерял: длительность записи по времени не сверялась; в исправленном `iso_capture` она печатается.

## Команды и станции

`cdc_send` шлёт кадры только из whitelist ([command-catalog.md](command-catalog.md)) и проверяет лимиты по расписанию до обращения к устройству. Захватывается только IF 3; IF 2 и запросы CDC не используются.
Проверено без устройства: `seek` отвергнут, `rai` через 5 с отвергнут. При первой сборке ошибка проверки чётности аргументов отвергала правильный вызов; исправлено до работы с Модулем.

| Проход | Отправлено | `0x22` после |
|---|---|---|
| 1 | `rai`, `band`, `rai` | AM cid 58 «1044 KHz» → FM cid 30 «90.5  MHz» → FM cid 30 |
| 2 | `tuneup`, `tuneup`, `rai` | FM cid 29 «90.4  MHz» → FM cid 28 «90.3  MHz» → FM cid 28 |

1. Гипотеза FM «МГц = 87,5 + 0,1 × cid» согласуется с третьей точкой: cid 28 → 90,3. Точки 28–31 соседние, края диапазона не проверялись.
2. Байт +7 длинного `0x24`: на 90,3 МГц — 0 в первом кадре после шага, затем 5 в шести кадрах и 4 в последнем; на 90,5 — 11, 11 сразу после BAND, затем 0–1; на 90,4 — 1. Это согласуется с тем, что +7 — уровень сигнала; гипотеза.
3. В этой сессии кадры ушли без DTR/RTS и line coding, и Модуль их выполнил. Влияние состояния, оставшегося от прошлых сессий с `usbser` в Windows, не исключено.
4. В начале прохода 1 — 3 байта мусора, обрывок 11 байт и 7 обрывков по 37 байт, SEQ скачет 63 → 164 → 12 → 39 → 66 → 108 → 172 → 218 → 195. Модуль около 19 минут после подключения копил кадры, пока порт никто не читал, и буфер переполнялся. Гипотеза.
5. После второго шага был ещё один спонтанный `0x22` с cid 28 (всего четыре в проходе 2).

В сессии работали версии программ с SHA-256 из журнала (`iso_capture.c` `7e784354…`, `cdc_send.c` `ecc64b66…`).
После ревью они исправлены: `cdc_send` прекращает отправку при ошибке чтения и считает интервалы по монотонным часам, `iso_capture` печатает длительность; добавлен `cdc_send --check`.
Строка журнала «FM 0x24 +7 = 4» относится к последнему кадру; полная последовательность — выше.

## Отклонения от плана

1. `usbipd bind --force`: обычный `bind` невозможен из-за фильтра USBPcap. Привязка действовала только для Модуля и снята после `detach`.
2. Повторные пробы драйвера — через sysfs `unbind`/`bind`, а не через `detach`/`attach` владельцем. Это те же стандартные запросы перечисления.
3. Сверх плана: `skip_validation=1`, kretprobe и function_graph — только наблюдение за ядром.
4. Сверх плана, с разрешения владельца: захват через libusb и отправка `rai`, `band`, `tuneup` через libusb. Первую попытку классификатор сессии отклонил; работа продолжена после прямого разрешения владельца.
5. `/proc/asound` недоступен в этом ядре.
6. `dmesg --time-format iso` пишет местное время (+03:00) и опережает журнал агента примерно на 27,5 минуты: например, переподключение через sysfs в 10:43:33Z в `dmesg` — 14:11:00 (+03:00). Причина не установлена. Порядок событий в `dmesg` верен, абсолютное время — нет.
7. Журнал `usbmon` остановлен вместе с шеллом, где запускался `pkill -f`: шаблон совпал с командной строкой самого шелла. Данные к этому моменту были записаны полностью.
8. Для захвата и отправки установлены `libusb-1.0-0-dev` 1.0.27 и `gcc` 13.2; первая установка была отклонена классификатором сессии.

## Что это значит для ГУ

1. Если на ГУ ядро 4.14 или 5.4 и его `mixer.c` так же отвергает эту топологию (не проверено), ошибка mixer остановит пробу и там. Тогда системный путь (`AudioRecord` с `TYPE_USB_DEVICE`) недоступен. Проверка — диагностическое приложение ([g2-probe-plan.md](../plans/g2-probe-plan.md)).
2. Рабочий путь — свой захват через libusb: разрешение USB, файловый дескриптор, IF 1 alt 1, iso EP `0x81`, поиск начала кадра в непрерывном потоке, компенсация дрейфа, `AudioTrack`. Нужен нативный код под `arm64-v8a`.
   Даже если системный драйвер на ГУ примет Модуль, кадры через границы пакетов могут дать перестановку каналов или щелчки.
3. Управление можно вести тем же устройством через bulk на IF 3; на ГУ Java API `UsbDeviceConnection.bulkTransfer` это умеет без нативного кода.
4. Если ГУ подключит свой `cdc_acm` или звуковой драйвер к интерфейсам Модуля, приложению придётся их отключать: libusb делает это через `detach_kernel_driver`, Java API — через `claimInterface(..., force=true)`.

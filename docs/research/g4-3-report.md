# G4-3: одна отправка TUNEDOWN

Дата: 14 октября 2026 года. Уровень воздействия E: команды из [command-catalog.md](command-catalog.md) по решению владельца.
Сбор выполнил Claude Code в Windows по [g4-3-windows-plan.md](../plans/g4-3-windows-plan.md); анализ выполнен в WSL.

## Итог

TUNEDOWN (`80 89`) повысил частоту на один шаг: cid 57 → 58, «1035 KHz» → «1044 KHz». Модуль вернулся на станцию до G4-2.
Ожидание из каталога подтвердилось: TUNEDOWN, который шлёт `onNext`, — шаг вверх. TUNEUP из G4-2 — шаг вниз.
Через 1,6 мс после TUNEDOWN пришёл один Кадр `0x22` с новой станцией, как после TUNEUP. Связь выведена по времени, наблюдение одно.
Гипотеза AM «522 + 9 × cid» согласуется уже с переходом в обе стороны; это те же две точки, 1035 и 1044 кГц.
Модуль помнит станцию без питания: между G4-2 и G4-3 его отключали, и он включился на 1035 кГц.

```text
19:20:30.3848 хост → requestAllInfo SEQ 0   +0,6…2,3 мс: 0x27, 0x22 cid 57 «1035 KHz», 0x24, 0x21
19:21:00.3842 хост → TUNEDOWN SEQ 1         +1,6 мс:     0x22 cid 58 «1044 KHz»
19:21:30.3683 хост → requestAllInfo SEQ 2   +0,6…2,2 мс: 0x27, 0x22 cid 58 «1044 KHz», 0x24, 0x21
```

| requestAllInfo SEQ 0 | −123 мс | +0,619 (60 Б), +0,884 (43 Б), +2,324 мс (31 Б) | SEQ 115 `0x27`, 116 `0x22`, 117 `0x24`, 118 `0x21` |

Предыдущий пакет здесь ближе, чем в G4-2 (−0,1 с против −0,85 с): фаза ритма 2 с случайна. Ответы не совпадают по времени с ритмом.

`0x22` за сессию; смещения +30 и +50 — от начала Кадра (`FA`), режим — `(тело[6]>>5)&3`:

| Поле | Старт (SEQ 7) | requestAllInfo (SEQ 116) | После TUNEDOWN (SEQ 151) | requestAllInfo (SEQ 185) |
|---|---|---|---|---|
| режим | 0 (AM) | 0 (AM) | 0 (AM) | 0 (AM) |
| cid | `00 39` = 57 | 57 | `00 3a` = 58 | 58 |
| текст | « 1035 KHz» | « 1035 KHz» | « 1044 KHz» | « 1044 KHz» |
| байт +30 | `0x16` | `0x00` | `0x00` | `0x16` |
| байт +50 | `0xae` | `0xae` | `0x00` | `0xae` |

Смысл байтов +30 и +50 не установлен. Спонтанный `0x22` после смены станции в G4-2 и G4-3 имеет +50 = `0x00`; в ответах на requestAllInfo +50 = `0xae`.
Список `0x21` не изменился: одна запись cid 58 «1044  KHz».
Сигнал `0x24` (байт +7 Кадра): 3 × 132, 4 × 9, без связи с отправками.

## Попутные наблюдения

1. Модуль помнит станцию без питания. G4-2 закончился на 1035 кГц, Модуль отключили; G4-3 начался на 1035 кГц.
   Где хранится станция, не установлено. Приложение при запуске должно читать станцию из `0x22`, а не считать её известной.
2. Потеря до открытия порта повторилась: 56 байт, SEQ 0–2, в 19:19:29.003, за 1,37 с до `Open()`.
   Сразу за ними хост отправил `SET_CONTROL_LINE_STATE` 0. Приём начался с SEQ 3 без мусора.
   Обёртку запустили в 19:19:28.14, событие — через 0,9 с. В G4-2 событие было тоже через 0,9 с после запуска скрипта.
   Гипотеза: данные читает сам процесс скрипта до `Open()`, например при `Get-PnpDevice` или создании `SerialPort`. Это касается Windows, а не ГУ.
3. Повторов пакетов USB, как в G4-2, нет.
4. `pnp-detached.txt` снят после подтверждения отключения, но показывает три устройства Модуля с `Present: True`. В G4-2 этот снимок был пустым.
   Трасса закончилась в 19:23:30, до отключения, и не помогает. Причина не установлена: Модуль не был отключён к моменту снимка или Windows не обновила список.

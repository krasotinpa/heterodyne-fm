# ADR 0001: звук — свой изохронный приём через usbfs

Статус: принято владельцем 15.10.2026. Пересмотр — по результату G2 и прототипа на ГУ.

## Контекст

1. Модуль отдаёт звук по USB Audio Class 1: IF 1 alt 1, изохронный EP `0x81`, асинхронный, 48 кГц, 16 бит, 2 канала ([descriptor-map.md](../research/descriptor-map.md)).
2. Дескриптор терминала ID 1 аномален: подтип Output Terminal при полях Input Terminal.
   Наблюдения: Windows не создала устройство записи; Linux 6.18 `snd-usb-audio` возвращает `-ENODEV` из `snd_usb_create_mixer` и удаляет карту ([g6a-report.md](../research/g6a-report.md)).
   Гипотеза: обе неудачи вызваны этой аномалией.
3. Свой захват через libusb на ПК с Linux дал звук: речь на FM 90,3 МГц, два захвата по ~30 с без плохих пакетов. Одно наблюдение; на Android не проверено.
4. Поток — непрерывные байты: кадры пересекают границы пакетов по 192 и иногда 198 байт. Во всех трёх захватах начало кадра было смещено на 2 байта; почему, не установлено.
5. Java API Android (`UsbDeviceConnection`, `UsbRequest`) по документации не поддерживает изохронные передачи; bulk и control поддерживает. На ГУ не проверялось.
6. Приложение производителя по статическому анализу читает поток через libusb (`libUSBAudio.so`, `libusb100.so`) и передаёт в нативный код файловый дескриптор и путь usbfs ([vendor-apk-analysis.md](../research/vendor-apk-analysis.md)). На этом ГУ оно не запускалось.
7. ГУ: Android 11 (API 30), вероятно SA8155P, ожидаемый ABI `arm64-v8a`; USB host не подтверждён ([g2-head-unit.md](../research/g2-head-unit.md)).

## Решение

1. **Звук.** Нативный код принимает изохронные URB через usbfs (`USBDEVFS_SUBMITURB`/`REAPURB`) на файловом дескрипторе открытого `UsbDeviceConnection`.
   Доступ — стандартное разрешение `UsbManager`; root не нужен.
2. **Захват интерфейсов.** IF 1 захватывается с `force = true` (системный драйвер, если занял интерфейс, отключается) и переводится в alt 1 через `setInterface`.
   IF 3 захватывается с `force = true` для bulk. IF 0 и IF 2 не захватываются. Управляющих запросов CDC (line coding, DTR/RTS) приложение не шлёт.
   Модуль принимал кадры без них в одной сессии G6a; влияние состояния от прошлых сессий с `usbser` не исключено. Это проверяется на ГУ.
3. **Радиокоманды.** Только из whitelist [command-catalog.md](../research/command-catalog.md), с его лимитами, через `bulkTransfer` на EP `0x03`, ответы — с EP `0x83`. ADR whitelist не расширяет.
4. **Кадры.** Начало кадра определяется после каждого `setInterface(alt 1)` и после любой ошибки или разрыва потока. Метод определения — задача прототипа; разбор не предполагает 192 байта в пакете.
5. **Вывод.** `AudioTrack` (`USAGE_MEDIA`, PCM 16 бит, 48 кГц, стерео).
6. **Сборка.** Нативная библиотека собирается NDK под `arm64-v8a`; `armeabi-v7a` — до подтверждения ABI в G2.
7. **Системный путь** (`AudioRecord` с `TYPE_USB_DEVICE`) не используется, пока G2 не покажет на ГУ USB-аудиовход Модуля.

## Почему usbfs, а не libusb

| Вариант | За | Против |
|---|---|---|
| usbfs напрямую | Без сторонних зависимостей; тот же механизм, что libusb на Linux | Своя работа: несколько URB в полёте, поток reap, discard при остановке, статусы пакетов, отключение устройства |
| libusb | Проверен в G6a на ПК; используется производителем | Сторонняя библиотека в сборке NDK |
| Системный USB-аудиовход | Без нативного кода | В Linux 6.18 не работает; на ГУ, вероятно, тоже |

libusb — запасной путь с меньшим риском ошибок в работе с URB. Если usbfs на ГУ недоступен приложению (SELinux, права), libusb не поможет: он использует тот же usbfs. Тогда это blocker G2.
Другие blocker G2: ГУ не объявляет `android.hardware.usb.host`; разрешение USB не выдаётся.

## Последствия

1. В проект входят NDK и нативный код; toolchain закрепляется в сборочном скрипте.
2. Файловый дескриптор живёт, пока открыт `UsbDeviceConnection`: нативный код останавливается до закрытия соединения.
3. Остановка: discard всех URB, reap, `setInterface(alt 0)`, освобождение интерфейсов, закрытие соединения.
4. URB рассчитаны на максимум EP: 312 байт на пакет.
5. Источник асинхронный, обратной связи нет: при долгой работе нужна компенсация дрейфа — подстройка по заполнению буфера (ресемплинг или вставка/выброс кадров). В прототипе не делается.
6. Нужны политики: аудиофокус, недогрузка `AudioTrack`, отключение USB, перезагрузка ГУ и повторное разрешение.
7. Диалог запроса USB-разрешения предупреждает, что приложение сможет записывать звук через USB-устройство: так Android ведёт себя без `RECORD_AUDIO` для устройств со звуковым классом.
   Решение — принять предупреждение, `RECORD_AUDIO` не запрашивать. Поведение диалога на ГУ проверяется в G2.
8. Прототип проверяется вместе с диагностическим приложением G2 одной поездкой. Звук на ГУ подтверждает решение; отказ usbfs или USB host — пересмотр.

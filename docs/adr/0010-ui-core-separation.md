# ADR 0010: граница UI и Core

Статус: Proposed.

## Контекст

Приложение собирается в одном `:app`. Compose может рисовать Эфир на тестовых данных. Рабочий запуск связывает экраны с объектами приложения, хранилищем и состоянием Приёмника. Сервис воспроизведения уже работает отдельно от экрана. [Аудит](../architecture/ui-core-audit.md).

## Проблема

Независимый разработчик не может собрать весь сменный интерфейс с одним публичным контрактом. Текущие границы заставляют его читать детали хранения, USB и режимов приложения. Действие, ожидаемая цель и физически подтверждённая частота имеют разные источники и требуют явных правил.

## Критерии выбора

1. UI собирается с контрактом и Sandbox.
2. Правила работы на ходу и аппаратные команды остаются у владельца операции.
3. Остаются прежние жизненные циклы USB, звука, руля и хранения.
4. Миграция проверяется и откатывается небольшими этапами.
5. Новую Возможность можно добавить после испытаний Приёмника.

## Рассмотренные варианты

| Вариант | Основной компромисс |
| --- | --- |
| Общий фасад и пакеты в `:app` | Быстрый первый шов. Зависимость от внутреннего кода всё ещё может компилироваться. |
| Отдельные контракт и UI, Core в Android host | Компилятор проверяет публичную границу. Понадобятся перенос UI и отдельный Sandbox. |
| Немедленный вынос Core в JVM | Больше кода проверяется как JVM. Нужно одновременно выделить Android-порты и перепроверить каждый жизненный цикл. |

## Предлагаемое решение

1. `:ui-contract` — Kotlin/JVM. Публикует снимок, типы действий и семантику состояний.
2. `:ui-compose` — Android library. Компилирует экраны с контрактом и зависимостями UI.
3. `:app` — Android host, Application Adapter и текущий Core. Host связывает сервис и экран, держит разрешения и жизненные циклы. Adapter переводит снимок и действия. Core постепенно освобождается от Compose Runtime.
4. `:ui-sandbox` — отдельное Android-приложение с тем же интерфейсом и сценарной подменой контракта. Preflight остаётся интеграционной проверкой приложения и `ReceiverFixture`.

```text
:app ──────────→ :ui-compose ──→ :ui-contract
  └─ adapter ──────────────────→ :ui-contract
:ui-sandbox ───→ :ui-compose
  └─ fake ─────────────────────→ :ui-contract
```

Граница выполняется внутри обычного процесса приложения. Замена UI означает подключение другой реализации при сборке. Обе реализации UI проходят обычное review вклада. Граница сборки защищает зависимости, а исполнение внутри общего процесса требует доверенного кода.

## Обоснование

Вариант с модулями закрывает доказанную проблему compile classpath. Один контракт нужен двум реализациям — production adapter и Sandbox. Сервис и внутренний `Receiver` уже имеют полезные границы. Отдельный Gradle-модуль для Core сейчас не даёт дополнительной независимости UI, а перенос усложнит проверку рабочих очередей и JNI.

## Последствия

Для UI понадобится отдельная сборка с метаданными контракта. Core отвечает за целостность снимка, допуск к операции и преобразование внутреннего результата. UI отвечает за оформление, локальную навигацию, доступность и отправку намерений. Допуск Стоянки и физический режим публикует host.

## Совместимость и миграция

Сохранить идентификатор штатного APK, JSON, ключи настроек, требования R01–R28 и политику аудиофокуса. Применить действующий whitelist к каждому действию, включая возврат на FM из Диагностики. Версия UI Contract независима от APK. Для первой версии пересобираются оба клиента. ADR 0007 и 0008 продолжают определять Приёмники и FM, ADR 0003–0005 — звук, потоки и запуск, ADR 0009 — Справочник. [Спецификация](../architecture/ui-contract-spec.md), [этапы](../plans/ui-core-separation.md).

## Риски

- Поздний callback после отключения может попасть в следующий сеанс. Сверять поколение и проверять гонку в контрактном тесте.
- Частое копирование больших Справочников и диагностических данных может замедлить Эфир. Переиспользовать стабильные данные и измерить отклик на ГУ.
- Guard может лишить водителя разрешённой кнопки руля или пропустить запоздалое действие Стоянки. Проверять источники действия отдельно.
- Sandbox может разойтись с production. Прогонять одни наблюдаемые контрактные случаи у двух реализаций.

## Открытые вопросы владельцу

1. Утвердить предложенные Gradle-модули и разделение host/Adapter/Core.
2. Подтвердить контракт для прямой частоты, явных Start/Stop и выдачи эффекта аудиофокуса по текущей политике.
3. Подтвердить отмену работ Стоянки. Предложение завершает начатый экспорт Журнала в фоне и скрывает результат до возвращения.
4. Выбрать, сохранять ли разные курсоры экрана и руля на первой миграции. Предложение сохраняет наблюдаемое поведение и переносит объединение в отдельную задачу.
5. Утвердить поставку UI SDK с версией и проверкой после пересборки. Публикацию бинарного SDK можно оценить при наличии внешнего потребителя.

## Критерии приёмки решения

1. UI и Sandbox компилируются без `:app`, USB и NDK. Контракт не зависит от Android/Compose.
2. Другой UI подключается в host через контракт без изменения Core. Производственная и сценарная реализации проходят общие контрактные тесты.
3. Подтверждение, цель, сохранённая частота и ограничения Стоянки выдерживают тесты ошибок, отмены, смены Приёмника и detach.
4. Preflight подтверждает штатные цепочки и фон на эмуляторе. Владелец проверяет реальный звук, руль, отклик и визуальную приёмку на ГУ.

# Права Codex в VS Code

Владелец работает в окне расширения Codex для VS Code.
Агент рекомендует уровень доверия для задачи и кратко объясняет нужный доступ.
Владелец выставляет уровень в интерфейсе расширения и принимает ответственность за выбранный вариант.
Это решение владельца от 17.11.2026 заменяет обязательные пары прав и запрет полного доступа в прежней инструкции.

## Выбор уровня доверия

Sandbox — ограничения команд агента на уровне операционной системы.
Approval policy — правило запроса разрешений на выход за эти ограничения.
Таблица задаёт рекомендации, а не обязательные условия начала работы.

| Задача | Рекомендуемый sandbox | Рекомендуемая approval policy | Назначение |
|---|---|---|---|
| Аудит | `read-only` | `never` | Чтение и анализ без повышения прав |
| Разработка | `workspace-write` | `on-request` | Изменения и проверки в отдельном worktree; выход за ограничения требует разрешения |

Владелец может выбрать другой доступный вариант, включая «Полный доступ» (`Full Access` / `danger-full-access`).
Агент сообщает известные фактические права и продолжает разрешённую работу в их пределах.
Отличие от рекомендации само по себе не служит причиной остановки или обязательного перехода в терминал.
Если точные параметры недоступны агенту, он сообщает это и работает в доступных пределах.
Название режима в интерфейсе не доказывает точное значение sandbox и approval policy.
Значения config.toml также не доказывают права текущего чата.

Выбранный уровень доверия не расширяет границы задачи и не отменяет ограничения проекта или среды выполнения.
При аудите разрешены только чтение и анализ, даже если выбран более широкий доступ.
Аудит не разрешает сборку, обновление графа, установку пакетов или изменение Git.
`never` само по себе не даёт полных прав: ограничения определяет sandbox.
Sandbox команд не ограничивает все действия подключённых MCP и внешних сервисов.
Поэтому агент также соблюдает границы задачи для каждого инструмента.
Сам клиент Codex может сохранять историю и служебные данные вне команд агента.
Режим аудита не означает нулевую запись всех процессов на компьютере.

## Работа в расширении

1. Открой нужный worktree через VS Code Remote WSL в `Ubuntu`.
2. Передай агенту задачу; агент рекомендует уровень доверия и объясняет выбор.
3. Выбери нужный уровень через управление правами текущего чата в расширении.
4. Агент проверяет доступные сведения о правах из инструкций среды и сообщает ограничения, которые мешают задаче.
5. Агент выполняет разрешённую работу; при фактическом отказе доступа использует доступный запрос разрешения или сообщает конкретный блокер.

Названия вариантов зависят от версии и локализации расширения.
Агент не меняет выбранный владельцем уровень и не требует повторного подтверждения уже принятого решения.
Если доступ подходит для следующей задачи, повторная настройка не нужна.
Ограничение конкретной операции не мешает выполнить независимые разрешённые действия.

При необходимости владелец может запросить проверку прав прямо в чате:

```text
Ничего не изменяй и не запускай команды.
Назови фактические sandbox_mode и approval_policy текущей сессии из инструкций среды.
Не используй значения config.toml. Если параметры недоступны, прямо сообщи об этом.
```

```text
Задача → рекомендация агента → выбор владельца в расширении → работа в доступных пределах
```

Не подменяй встроенный CLI Extension через `chatgpt.cliExecutable` ради выбора прав.
Агент выполняет необходимые команды через свои инструменты; владельцу не требуется вводить их в терминале.

## Необязательные CLI и задачи VS Code

CLI — интерфейс командной строки; он доступен по желанию владельца.
Работа в расширении не требует запуска CLI или переноса задачи в терминал.
Команды выполняются в WSL2, дистрибутив `Ubuntu`, из папки нужного repository или worktree.
Для разработки используй отдельный worktree по [процессу Codex](codex-implementation.md).

```bash
# Аудит
python3 build-support/codex-project.py --config 'sandbox_mode="read-only"' --config 'approval_policy="never"'

# Разработка
python3 build-support/codex-project.py --config 'sandbox_mode="workspace-write"' --config 'approval_policy="on-request"'
```

Задачи [tasks.json](../../.vscode/tasks.json) доступны через `Terminal → Run Task`:

1. `Codex: audit (read-only)` — аудит.
2. `Codex: develop (workspace-write)` — разработка.

Они запускают [проектный launcher](../../build-support/codex-project.py), который выбирает CLI из WSL `PATH` и отключает ненужные MCP только для запуска.
Эти задачи не переключают права и интеграции Extension; см. [инструкцию интеграций](project-integrations.md).
Для диагностики CLI доступны `/status` и `/debug-config`; их выполнение не требуется для работы в расширении.

## Источники настроек и диагностика

Общие значения по умолчанию хранятся в отслеживаемом [`.codex/config.toml`](../../.codex/config.toml).
Новые worktree получают его из коммита; копирование локальных настроек между worktree не требуется.
Codex применяет этот файл только для доверенного проекта.
Подтверждение доверия хранится на машине пользователя и не переносится через Git.
Флаги CLI имеют приоритет над проектными и пользовательскими значениями по умолчанию.
Явные флаги выше задают рекомендуемые права отдельного запуска CLI; выбор в расширении остаётся за владельцем.

### Общие и личные настройки

| Где | Что хранить |
|---|---|
| `.codex/config.toml` в Git | Согласованные значения проекта без секретов и машинных путей |
| `~/.codex/config.toml` вне repository | Личные провайдеры, MCP, машинные пути и решения о доверии |
| Хранилище авторизации Codex | Данные входа; они не входят в проектный config |

Личные модель и effort задавай через интерфейс текущей сессии или явные флаги CLI.
Пользовательский config не переопределяет совпадающие ключи доверенного проектного слоя.
Не добавляй личные правки в отслеживаемый config ради отдельной сессии.
Файл `.codex/config.local.toml` не является используемым здесь механизмом загрузки.
Глобальные провайдеры и MCP не копируются в Git и не меняются этой задачей.

Проект не задаёт `model_context_window`: без ручного переопределения Codex использует размер контекста выбранной модели.
Личные явные переопределения в других слоях возможны; удаление проектного ключа не отменяет их.
Проверка отсутствия ручного значения описана в [отчёте пункта 3/P1](../validation/codex-auto-context-p1.md).
Проектный config задаёт значения по умолчанию и не отменяет ограничения среды или политику активного чата.

### Существующая неотслеживаемая копия

Git может остановить обновление `main`, если на месте нового tracked config уже лежит неотслеживаемый файл.
Это происходит даже для одинакового содержимого; не используй принудительное перезаписывание.

1. Проверь `git status --short` и сравни локальный файл с входящим config.
2. Сохрани локальный файл в новый файл внутри игнорируемой `.scratch/` и проверь SHA-256 обеих копий.
3. При совпадении с входящим config убери только неотслеживаемый оригинал после проверки резервной копии.
4. При различиях сохрани личные параметры отдельно и остановись до решения, какие значения нужны.
5. Выполни обновление `main` и проверь, что config теперь отслеживается Git.

```text
Локальная копия → сравнение → резервная копия → обновление main → config из Git
                    └─ различия → сохранить отдельно и определить назначение параметров
```

Этот порядок относится к локальной синхронизации после merge PR по действующим полномочиям.

Проверить загрузку настроек CLI можно без запроса к модели:

```bash
python3 build-support/codex-project.py --config 'sandbox_mode="read-only"' --config 'approval_policy="never"' doctor --json
python3 build-support/codex-project.py --config 'sandbox_mode="workspace-write"' --config 'approval_policy="on-request"' doctor --json
```

`doctor` проверяет собственный запуск. Поле `active thread overrides: not inspected` исключает вывод о правах открытого чата.
Даже `overallStatus: ok` не подтверждает права Extension или исполнение всех ограничений.
Успешный тест записи внутри worktree не подтверждает запрет записи во все остальные папки.

Во время аудита 16.11.2026 CLI сообщал ограниченный sandbox и `OnRequest`.
Активная сессия агента имела `danger-full-access` и `never` из параметров среды выполнения.
Редактирование config не меняет права уже работающего чата.
Эта историческая проверка не задаёт обязательный уровень доверия для новых задач.
Новый запуск с явными флагами задаёт права отдельной CLI-сессии; в Extension владелец выбирает доступ через интерфейс.

Для отката режимов запуска используй revert PR P0.
Для отката версионирования config используй revert PR первого P1, затем восстанови локальную копию из backup при необходимости.
Такой откат не меняет права существующих чатов и пользовательский config.

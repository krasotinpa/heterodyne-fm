# Реализация через Codex

Codex реализует тикет `ready-for-agent`. Claude проверяет результат, ревьюит его и доводит до коммита.
Процесс перенесён из `netbox-scripts-and-reports` и согласован с разделом «Реализация и review» в [AGENTS.md](../../AGENTS.md).

## Что делает Codex, что — нет

1. Codex пишет код и тесты по тикету. Один тикет — один Codex-запуск в одном worktree.
2. Codex не работает с оборудованием. Он не открывает USB-Модуль и не шлёт radio TX.
3. Тикеты `ready-for-human` (например, приёмка на ГУ) Codex не берёт.
4. Новые команды в whitelist Codex не добавляет. Whitelist ведёт владелец в `docs/research/command-catalog.md`.
5. Код проверяют на fake transport. Реальный Модуль и ГУ проверяет человек в тикете приёмки.

## Промпт для Codex

1. **Сначала тикет.** Передай номер: `gh issue view <N> --comments`. Критерии приёмки тикета задают границы задачи.
2. **Спецификация.** Укажи нужные R-строки в [requirements.md](../requirements.md) и раздел [architecture.md](../architecture.md). Не пересказывай их.
3. **Образец.** Назови уже слитую соседнюю реализацию, которую надо повторить. Не описывай форму с нуля.
4. **Сначала тест.** Codex пишет тест, запускает его и видит падение по ожидаемой причине. Затем реализует до зелёного.
5. **Без коммита.** Worktree остаётся незакоммиченным. Коммитит сессия Claude после проверки и ревью.
6. **Правила репозитория.** Codex читает [AGENTS.md](../../AGENTS.md): безопасность radio TX, доказательства, redaction.

## Запуск через `/implement #N`

Владелец запускает каждый тикет в новой сессии: `mattpocock-skills:implement #<issue>`.
Скилл сам не знает правил репозитория. Эти шаги имеют приоритет над его текстом.

1. Прочитай тикет: `gh issue view <N> --comments`. Проверь, что тикет не `ready-for-human`.
2. Проверь блокирующие тикеты. Если хоть один открыт, остановись и сообщи об этом.
   Сравни строку «Затрагивает файлы» с другими открытыми PR и тикетами в работе. При общем файле остановись и сообщи об этом.
3. Убедись, что ты не в `main`. Создай feature-ветку и worktree по разделу «Worktree».
4. Передай код Codex по разделу «Промпт для Codex». Сам код в этой сессии не пиши.
5. Выполни независимую проверку и ревью по разделам ниже. Вместо `/code-review` скилла используй порядок из «Ревью».
6. Закоммить в feature-ветку. Перед `git push` выполни `git fetch` и `git merge origin/main`. Реши конфликты сам и повтори gate по разделу «Независимая проверка».
7. Выполни `git push` ветки и открой PR в `main`. Merge выполняет владелец.
8. В PR укажи `Closes #<N>`, фактические exit code проверок и список непроверенного.

## Worktree

1. Создай worktree вручную от актуального `main`: `git worktree add ~/worktrees/<name> -b <branch> main`.
2. Режим изолированного worktree у субагента Claude несовместим с фоновыми заданиями Codex.
3. Запускай `codex-companion.mjs task` (или `/codex:rescue`) против этого worktree из вызывающей сессии. Не используй обёртку-субагент.
4. В свежем worktree нет `graphify-out/`. Сначала выполни `graphify update .`, когда в проекте появится код.
5. Тикеты, которые меняют одни и те же файлы, не запускай параллельно. Следуй цепочке «Blocked by».
6. Каждый тикет имеет строку «Затрагивает файлы». Автор тикета перечисляет в ней файлы, которые агент меняет с высокой вероятностью. Если два тикета делят файл, автор добавляет «Blocked by» от одного к другому.

## Порядок merge параллельных PR

1. Владелец сливает PR по одному. Первым идёт PR, который меняет больше всего общих файлов.
2. После каждого merge исполнитель каждого из оставшихся PR выполняет `git fetch` и `git merge origin/main` в своей ветке. Затем он повторяет gate и делает `git push`.
3. Исполнитель не копит несколько merge из `main`. Один конфликт решается проще, чем четыре сразу.
4. В настройках GitHub включи «Require branches to be up to date before merging». Тогда устаревший PR нельзя слить без обновления.

## Независимая проверка

После каждого тикета Claude сам выполняет проверки из [test-plan.md](../test-plan.md) в своей сессии:
`./gradlew test lint assembleDebug` и Python-тесты для `research-tools/`.
Отчёт Codex «всё зелёное» не считается проверенным, пока эти команды не прошли в сессии Claude.
Записывай фактический вывод и exit code.

## Ревью

1. **Adversarial review от Codex.** Выполни его после тикета и до ревью Claude: `codex-companion.mjs adversarial-review` или `/codex:adversarial-review`. Шаг обязателен для любого размера задачи.
2. **Проверка замечаний.** Оценивай каждое замечание по доказательствам: код, критерии тикета, requirements. Не принимай и не отклоняй автоматически.
3. **Ревью Claude.** Независимое ревью Claude идёт после adversarial review. Ревью Codex его дополняет и не заменяет.
4. **Один цикл.** Reviewer только читает. Исполнитель объединяет fixes в один пакет, затем выполняется один повторный gate. Новый цикл нужен только при существенных новых findings.

```text
Тикет → worktree → Codex: тест, код → Claude: gate
      → Codex: adversarial review → Claude: ревью → fixes → gate → коммит и PR
```

## Модели

Claude выбирает нижнюю границу модели для проверки по таблице в [CLAUDE.md](../../CLAUDE.md). В тикетах эта граница записана в строке «Исполнитель».

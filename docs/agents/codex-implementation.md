# Разработка только с Codex

Codex ведёт задачу от критериев приёмки до PR. Merge выполняет владелец.
Правила оборудования и полномочия заданы в [AGENTS.md](../../AGENTS.md).

## Начало задачи

1. Прочитай Issue с комментариями и метками через `gh issue view <N> --comments`.
2. Бери задачи `ready-for-agent`. Задачи `ready-for-human` выполняет человек.
3. Проверь открытые зависимости, включая native dependencies GitHub и строку «Blocked by».
4. Сравни строку «Затрагивает файлы» с открытыми PR и задачами в работе.
5. При открытом блокере или конфликте файлов сообщи препятствие до реализации.
6. Прочитай указанные требования, архитектуру, CONTEXT.md и относящиеся к задаче ADR.

Прямая задача владельца в чате также задаёт границы работы. Не создавай Issue только ради запуска процесса.

## Worktree и инструменты

1. Проверь дистрибутив WSL, repository, branch, worktree и SHA.
2. Выполни `git fetch origin`. Создай feature-ветку в отдельном WSL worktree от `origin/main`.
3. Перед первым изменением кода прочитай и примени `ponytail full`.
4. Для поиска по коду сначала выполни `graphify update .`, затем `graphify query "<вопрос>"`.
5. Проверяй вывод графа по исходникам. Точные строки и символы ищи через `rg`.
6. Храни граф только в игнорируемом `graphify-out/` текущего worktree.

Скиллы Codex находятся в `~/.codex/skills/`. Их инструкции дополняют правила проекта.
Claude, `codex-companion.mjs` и команды Claude не входят в обязательный процесс.

## Реализация и проверка

1. Один исполнитель реализует связный блок. Задачи с общими файлами выполняй последовательно.
2. Проверяемое поведение реализуй test-first: ожидаемое падение теста, минимальный код, успешный тест.
3. Код оборудования проверяй через fake transport. Codex не открывает USB-приёмник и не выполняет radio TX.
4. Новые записи whitelist утверждает владелец. Приёмку на ГУ выполняет человек.
5. Выполни один полный local validation gate по [test-plan.md](../test-plan.md).
6. Запиши фактические команды, вывод, exit codes, base/head SHA и непроверенные пункты.

## Независимое review

После успешного gate выполни одну независимую review-волну всей ветки агентами Codex.
Используй скилл `code-review`: независимые проверки правил и соответствия задаче идут в одной волне.
Передай reviewer точный base/head SHA, весь diff, задание владельца или Issue и отчёт gate.
До первого коммита HEAD обозначает базу, а реализация находится в рабочем дереве.
Для этого случая правило проекта переопределяет сравнение скилла `code-review`:

1. Зафиксируй base SHA и выполни `git diff <base-SHA>`: команда включает staged и unstaged изменения отслеживаемых файлов.
2. Получи новые файлы через `git ls-files --others --exclude-standard` и передай их содержимое reviewer отдельно.
3. Передай список всех файлов проверки. Сохрани снимок diff и SHA-256 проверяемых файлов в `.scratch/`.
4. Во время review сохраняй рабочее дерево неизменным. После review меняй его только пакетом исправлений.

Если реализация уже закоммичена, используй сравнение скилла `git diff <base-SHA>...HEAD`.
Reviewer только читает и сообщает findings. Он не меняет код.

Исполнитель оценивает замечания по исходникам и требованиям, затем исправляет их одним пакетом.
После исправлений выполни один повторный gate.
Новая review-волна нужна только при существенных новых findings или изменении требований.

## Коммит и PR

1. Codex коммитит проверенные изменения в feature-ветку.
2. Перед push выполни `git fetch origin`. Если `origin/main` изменился, влей его в feature-ветку.
3. После такого обновления повтори gate. Существенные изменения требуют нового review.
4. Выполни push feature-ветки и открой PR в `main`.
5. Укажи `Closes #<N>`, если задача имеет Issue, результаты проверок и ограничения.
6. Merge выполняет владелец. Прямой push в `main` запрещён.

```text
Задача → worktree → Ponytail → тест и код → полный gate
       → независимое review Codex → fixes → повторный gate → коммит → PR → merge владельцем
```

## Параллельные PR

Владелец сливает PR по одному. После merge исполнитель оставшейся ветки обновляет её из `origin/main`.
Он решает конфликты и повторяет gate до следующего merge.

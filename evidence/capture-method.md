# Super Radio AM/FM — методика получения `super-radio-com5.bin`

**Назначение:** воспроизвести сбор исходных данных и правильно интерпретировать файл при reverse engineering USB AM/FM-приёмника для Android-ГУ Toyota Highlander 2026.

**Источник:** фактические команды PowerShell и результаты, предоставленные владельцем устройства в переписке 14.10.2026; бинарный файл проверен отдельно. Эта справка описывает **наблюдаемый эксперимент**, а не предполагаемую внутреннюю архитектуру приёмника.

## 1. Оборудование и среда

- Устройство: внешний USB AM/FM-приёмник **Super Radio** (надпись на корпусе `Super Radio — Applied to Android System`), с внешней антенной; продавался на Ozon под артикулом **3312782920**.
- Приёмник подключался к **Windows-компьютеру**, а **не к автомобилю**.
- Windows-компьютер: `<redacted-host>` (имя из диагностического вывода). Точная версия Windows и PowerShell при записи не зафиксированы; версия системного драйвера `10.0.22621.3672`.
- USB VID:PID: `0483:5740`; аппаратные ID `USB\VID_0483&PID_5740&REV_0200`, `USB\VID_0483&PID_5740`.
- USB product string: `DAB usb bridge`.
- Составное USB-устройство: интерфейс `MI_00` отображался как `DAB usb bridge`, `MI_02` — как `USB Serial Device (COM5)`.
- Драйвер интерфейса COM5: штатный Microsoft **usbser**, `usbser.inf`; отдельный драйвер производителем в Windows не устанавливался (по представленным данным).
- Физическое подключение антенны во время записи **не подтверждено**; не следует предполагать наличие приёма радиостанций.

> `0483` относится к STMicroelectronics; `5740` не является уникальным идентификатором конкретного радиопротокола или APK. `DAB usb bridge` — строка USB-устройства, а не доказательство поддержки DAB в приобретённой AM/FM-версии.

## 2. Обнаружение последовательного интерфейса

## 3. Предварительное чтение COM5

Сначала COM5 открывался с параметрами **115200, 8N1**, без flow control, с `DtrEnable = $false` и `RtsEnable = $false`. В течение 10 секунд выполнялось чтение входящих байтов и вывод в hex. Данные поступали без явной записи пользовательских команд в порт.

Это установило, что последовательный интерфейс выдаёт бинарный поток с повторяющимися маркерами `FA 55`. Предварительное чтение **не было** исходником прикреплённого `.bin`: `.bin` получен отдельной последующей записью в течение 30 секунд.

## 4. Точный скрипт, которым создавался `.bin`

В PowerShell выполнен следующий скрипт:

```powershell
$path = "$env:USERPROFILE\Desktop\super-radio-com5.bin"

$port = [System.IO.Ports.SerialPort]::new(
    'COM5', 115200,
    [System.IO.Ports.Parity]::None,
    8,
    [System.IO.Ports.StopBits]::One
)

$port.DtrEnable = $false
$port.RtsEnable = $false
$port.ReadTimeout = 500

$stream = [System.IO.File]::Create($path)

try {
    $port.Open()
    $end = [DateTime]::UtcNow.AddSeconds(30)

    while ([DateTime]::UtcNow -lt $end) {
        $count = $port.BytesToRead

        if ($count -gt 0) {
            $buffer = [byte[]]::new($count)
            $read = $port.Read($buffer, 0, $count)
            $stream.Write($buffer, 0, $read)
        }

        Start-Sleep -Milliseconds 20
    }
}
finally {
    if ($port.IsOpen) { $port.Close() }
    $port.Dispose()
    $stream.Dispose()
}

Write-Host "Saved to $path"
```

### Что делает скрипт

1. Создаёт файл `%USERPROFILE%\Desktop\super-radio-com5.bin` (в эксперименте пользовательский профиль `C:\Users\<redacted-user>`). **Если файл уже существует, `File.Create` перезапишет его.**
2. Настраивает `System.IO.Ports.SerialPort`: COM5, **115200 baud, 8 data bits, no parity, 1 stop bit**; handshake по умолчанию `None`.
3. Устанавливает `DtrEnable = false`, `RtsEnable = false`, `ReadTimeout = 500 ms`.
4. Открывает порт, в течение примерно **30 секунд** каждые 20 мс проверяет `BytesToRead`, читает имеющиеся байты и записывает их в файл **без преобразования**.
5. Закрывает порт и файловый поток через `finally`.

Скрипт **не вызывает** `SerialPort.Write`, не передаёт команд настройки частоты и не производит преднамеренной записи в устройство. Однако само открытие COM-порта может влиять на состояние некоторых устройств; эксперимент нельзя считать строго пассивным на физическом уровне.

**В файл НЕ включены:** заголовок, дата/время, скорость порта, USB-дескрипторы, границы отдельных вызовов `Read`, временные метки между пакетами, исходящий USB-трафик или лог ошибок. Это просто последовательная конкатенация прочитанных байтов.

## 5. Характеристики фактически полученного файла

Файл: `super-radio-com5.bin`

- Размер: **1720 байт**.
- SHA-256: `f1697ad37d944abf4b1d09537caca7bd6f370793dd9aa3cc60b0f2a738e70d3d`.
- Начальные байты:

```text
FA 55 B7 00 14 26 04 00 20 20 20 20 20 20 20 20 ...
```

При проверке содержимого установлено **104 полных кадра**, из них:

| Первый байт данных | Число кадров |
|---|---:|
| `0x24` | 49 |
| `0x26` | 49 |
| `0x29` | 6 |

Ниже — **проверяемая гипотеза** формата кадра:

```text
FA 55 | SEQ (1 byte) | LEN (2 bytes, big-endian) | BODY (LEN bytes)
```

- `FA 55`: двухбайтовый синхромаркер.
- `SEQ`: изменяющееся однобайтовое поле (похоже на счётчик, назначение не доказано).
- `LEN`: двухбайтовая длина `BODY`, включая последний байт контрольной суммы.
- `BODY[0]`: предполагаемый тип сообщения (`24`, `26`, `29`).
- `BODY[-1]`: предполагаемая контрольная сумма, для всех 104 кадров выполняется `sum(BODY) % 256 == 0`.

Примеры **полных** кадров:

```text
FA 55 B8 00 04 24 00 00 DC
FA 55 B7 00 14 26 04 00 20 20 20 20 20 20 20 20 20 20 20 20 20 20 20 20 D6
```

Важное исправление относительно ранних предположений: `00 14` — длина **20 байт**, включая `D6`, а не длина только полезной нагрузки; последний байт `D6` входит в поле `BODY`. Сумма `BODY` равна нулю по модулю 256. Типы сообщений, значение байтов `04 00`, назначение ASCII-пробелов `20` и связь с реальным FM/RDS пока не расшифрованы.

### Минимальный проверочный Python-скрипт

```python
from pathlib import Path
from collections import Counter
import hashlib

p = Path('super-radio-com5.bin')
data = p.read_bytes()
print('bytes:', len(data))
print('sha256:', hashlib.sha256(data).hexdigest())

offset = 0
counts = Counter()
while offset < len(data):
    assert data[offset:offset + 2] == b'\xfa\x55', offset
    length = int.from_bytes(data[offset + 3:offset + 5], 'big')
    end = offset + 5 + length
    assert end <= len(data), ('truncated', offset)
    body = data[offset + 5:end]
    assert body and sum(body) % 256 == 0, ('checksum', offset)
    counts[body[0]] += 1
    offset = end

print('frames:', sum(counts.values()))
print('types:', {hex(k): v for k, v in counts.items()})
```

Ожидаемый результат: `bytes: 1720`, `frames: 104`, `types: {'0x26': 49, '0x24': 49, '0x29': 6}` (порядок отображения может отличаться).

## 6. Ограничения эксперимента

1. **Не USBPcap:** файл содержит только входящие данные COM5, а не полную USB-трассу. Нет команд host→device, USB endpoints, дескрипторов и аудиоданных других интерфейсов.
2. **Не дамп firmware:** содержимое не является образом памяти STM32 или другого чипа.
3. **Не доказана радиофункция:** в записи не было управляемой настройки частоты или наблюдаемого приёма звука; пакеты могут быть heartbeat/status.
4. **Не установлено назначение `MI_00`:** может использоваться для управления, аудио, отладки или других задач; нужны USB-дескрипторы.
5. **Скорость 115200 выбрана для теста:** успешное чтение и корректная структура пакетов согласуются с параметрами, но CDC ACM может игнорировать виртуальную скорость линии.
6. **Отсутствуют временные метки:** нельзя достоверно вычислить частоту пакетов по одному файлу; известна лишь длительность окна записи около 30 секунд.
7. **Управление DTR/RTS:** значения выставлены в `false`, но открытие порта может инициировать служебные USB-запросы со стороны драйвера.
8. **Совместимость Android-ГУ не проверена:** наличие USB-порта Toyota не гарантирует Android USB Host и доступ приложения к USB-интерфейсу.

## 7. Рекомендации агенту

1. Сохранить исходный `.bin` неизменным, фиксировать SHA-256; не подменять его результатами декодирования.
2. Реализовать и покрыть тестами parser framing `FA 55`, счётчик/поле `SEQ`, длину, проверку контрольной суммы и ресинхронизацию на повреждённых кадрах.
3. Получить полные USB configuration/interface/endpoint descriptors для `0483:5740` на Windows или Linux, **без записи неизвестных команд**.
4. Определить, что обслуживает `MI_00`, и каким образом передаётся звук (USB Audio Class, vendor-specific USB или иной тракт).
5. Дождаться ответа продавца с родным APK и инструкцией; при получении исследовать разрешения, USB-фильтры, используемые endpoints и протокол в контролируемой среде.
6. Перед активными тестами составить таблицу допустимых команд и процедуру восстановления устройства; исключить firmware update, erase, reset-to-bootloader и другие потенциально опасные операции без отдельного согласования.
7. Проверить Android USB Host, выдачу USB permission и доступность устройства на штатном ГУ Toyota Highlander 2026, прежде чем обещать работоспособность APK.

## 8. Происхождение файла и воспроизводимость

Файл создан **пользователем на его Windows-компьютере** приведённым выше PowerShell-скриптом и загружен в беседу. Анализ выполняется над этой загруженной копией. Дата создания файла в файловой системе контейнера не является достоверным временем первоначальной записи на Windows. Оригинальная дата/время запуска эксперимента, физическая конфигурация антенны и версия прошивки модуля не документированы.

Для повторного сбора рекомендуется создать **новый файл с уникальным именем**, записать UTC-время начала/конца, версию ОС/PowerShell, состояние антенны и модульной индикации, а также отдельно сохранять сырые байты и журнал наблюдений. Не следует перезаписывать оригинал.
